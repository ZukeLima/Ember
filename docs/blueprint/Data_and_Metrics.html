Contract assumptions

Monetary fields are decimal with two places in a single currency (BRL); timestamps are stored in UTC; all business IDs are strings; quantity > 0; unit price and refund amount are nonnegative. Refunds are attached to items to support correct allocation.

!

Modeling gap to settle before code. The MVP does not model payment authorization, taxes, shipping, discounts or chargebacks. Therefore its gross_revenue is eligible merchandise sales rather than accounting revenue recognized under a formal standard.

Time semantics, a material business decision

The default dashboard is order-cohort reporting: refunds adjust the original order's date, so historical net sales may change as late refunds arrive. A refund-cashflow view by refund date is explicitly out of scope for MVP.

Data-quality policy

Severity and outcome

SeverityConditionsOutcome CriticalDuplicate primary keys after dedupe, missing required foreign keys, negative amounts, financial reconciliation mismatchFail build and do not publish marts WarningMissing optional segment, delayed batch, unexpected but parseable statusReport warning; map optional values to unknown AcceptedOut-of-order deliveries with newer updated_at, valid partial refundsDeterministic upsert/rebuild

Deterministic deduplication

For source order snapshots, choose max updated_at, then a stable tie-breaker (source_sequence, then raw-record hash). If two conflicting values share the same business key and tie-breaker, fail rather than silently choose a row. The synthetic generator must include these fields.

Incremental implementation choice

First implement full-refresh materialization and verify correctness. Only switch a model to incremental after tests prove late updates, deletions and replay are handled. Incremental processing is an optimization, not a requirement for the first release.

Test scenarios

Nine cases the models must pass

  1. Duplicated input batch → same final counts/sums after replay.
  2. Order transitions from completed to cancelled → its contribution disappears on reprocess.
  3. One order with three items → order count stays one.
  4. One item with two partial refunds → gross counted once, both valid refunds counted.
  5. Refund greater than item value → quality gate fails.
  6. Missing customer reference → quality gate fails.
  7. Zero completed orders → AOV is NULL, not division error.
  8. Late refund → original order date's net sales is corrected.
  9. Two conflicting snapshots at identical ordering keys → load rejected explicitly.
